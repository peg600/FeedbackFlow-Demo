# 0003 — 数据库约束与事务保护业务一致性

本记录中 50 条配额及“尚无 Pro 解锁”描述的是当时的历史实现。后续 Paddle 权益见 [0011](0011-local-entitlements-and-reconciliation.md)，2026-09-30 的 3 条 Free 配额调整见 [0018](0018-three-item-free-feedback-limit.md)；项目级锁和数据库约束决策继续有效。

## 背景与约束

核心版本每个用户只能拥有一个项目，Slug 全局唯一，每个用户对同一反馈只能投一票。反馈创建还有每项目 50 条上限。前端禁用按钮或先查询再写入都无法排除跨请求并发，必须让数据库参与保证一致性。

## 考虑过的方案

- 仅在应用层预检查：可以给出友好提示，但两个请求可能同时通过，因此不能作为唯一保障。
- 对单行或唯一性使用数据库约束：适合 owner、Slug、投票组合等不变量；采用。
- 查询数量与插入仅放在普通事务中：不能单凭事务消除“两个请求都看到 49 条”的竞争。
- 项目级事务 advisory lock：当前采用。2026-09-16 对话讨论过对项目行 `SELECT ... FOR UPDATE` 的替代方案，没有切换实现的指令；不能把后续讲解写成最初选型过程。

## 决策与理由

项目 owner 和 Slug 使用命名唯一索引；投票使用 `(userId, feedbackId)` 复合主键。项目创建、投票插入保留 `onConflictDoNothing`，在冲突后区分重复提交、资源已存在与真正的业务冲突，避免把所有重复请求都变成系统错误。

反馈创建在事务中获取以项目 ID 为键的 `pg_advisory_xact_lock`，随后复核项目公开范围、计数并插入。当前所有项目仍受 50 条限制，尚无真实 Pro 订阅解锁；不能根据 UI 套餐文案绕过限制。

## 影响与代价

- 唯一约束保护并发下的最终数据；应用预检查继续负责权限和可展示的业务错误。
- 50 条配额不是数据库声明式约束，所有反馈写入必须调用共享写入函数或遵守同一加锁协议。锁按项目串行化相关临界区，不是全库锁，也不保证 HTTP 请求到达顺序。
- advisory lock 不自动锁住项目行，不能替代外键、公开性复核或其他写路径的正确处理。项目 ID 哈希碰撞可能造成无关项目额外等待。
- 需要保持外键、唯一索引、迁移及业务错误映射一致。

## 实施与验证

约束存在于 schema 和初始 migration；共享写入函数包含完整锁、复核、计数和插入过程，Demo Seed 使用同一项目锁协议。现有单元测试覆盖冲突分支，集成用例定义了 49 条已有反馈时并行写入的上限行为及投票唯一性。2026-09-18 的历史交付明确说明真实 Neon 集成测试尚待执行；本次也没有运行数据库测试。

## 重新评估条件

新增导入、批量写入、真实套餐配额或高并发项目时，需要重新验证所有写路径的协调协议；若改用行锁或计数器，应新增替代记录并做并发测试。
