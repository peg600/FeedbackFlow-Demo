# 0005 — URL 驱动服务端列表与派生路线图

- 状态：Accepted

- 决策日期：2026-08-20—2026-09-18 分步落地（首次提出 URL 方案的独立讨论日期未确认）
- 记录性质：历史补录
- 替代：无
- 被替代：无

## 背景与约束

Dashboard、公开反馈板和 Roadmap 都围绕同一批反馈。列表需要搜索、筛选、排序、分页，并在刷新、链接分享、Owner 更新状态或修改 Slug 后保持一致。路线图不需要独立的维护入口，产品范围也没有拖拽排序等额外状态。

## 考虑过的方案

历史实现采用 URL 查询参数和服务端读取；没有找到首次选择时对客户端状态仓库、独立查询 API 等方案的完整比较，因此不将这些写成曾正式评审过的替代方案。

2026-09-18 的已确认完善方案明确选择：Roadmap 每栏显示有限预览与总量，“View all”复用已有分页反馈板，而不是在路线图中无限展开所有反馈。

## 决策与理由

筛选、搜索、排序和页码放入 URL Search Params，服务端解析并限制输入，Client Component 负责改变 URL。查询在服务端组合公开性、项目归属及筛选条件，采用包含稳定次序的排序，页码限定到实际范围。

Roadmap 从公开反馈的 `planned`、`in_progress`、`completed` 状态直接派生，不维护独立路线图表。每栏最多 4 项及总数，查看全部跳转到带相应状态的反馈板。

项目设置保存后使用服务端实际结果更新表单，刷新 Dashboard 导航以及新旧 Slug 相关公开路径；投票、状态变更等操作继续维护相关页面刷新。这样可分享的 URL 与读模型更新遵守同一数据来源，而不是维护多份客户端业务副本。

## 影响与代价

- URL 可以恢复查询状态，公开列表与路线图无需额外状态同步表。
- 切换筛选涉及导航和服务端查询；需要明确 loading、空状态、非法参数及超范围页码行为。
- Slug、公开性和状态变化涉及多个读取入口，遗漏失效路径会产生旧导航或旧展示。
- Roadmap 的有限预览控制返回规模，但不构成任意数据规模下的性能保证。

## 实施与验证

当前公开反馈板和 Dashboard 有参数解析、服务端查询及分页；路线图服务按状态聚合总量和预览。现有页面/筛选测试与缓存路径测试覆盖相关导航和失效行为；真实查询性能及大数据规模未在本次验证。

## 重新评估条件

需要独立路线图条目、复杂拖拽排序、跨页面实时状态，或实测查询规模成为瓶颈时重新评估读模型与缓存策略。
