## 背景与约束

公开演示需要限制注册、登录、反馈提交和投票滥用。2026-09-18 的完善方案要求共享服务端限流，保留已有配额与权限校验，并复用 PostgreSQL，不为当前规模引入 Redis。用户随后同意按该方案实现。

## 考虑过的方案

- 每个进程内独立计数：不能提供多个应用实例共享的配额，也无法替代已要求的共享限流。
- 增加 Redis：历史方案明确选择先复用现有数据库，避免新增基础设施。
- PostgreSQL 固定窗口与单条原子 UPSERT：实现采用此方案。具体算法是在实施中确定，根会话没有完整的算法比较记录，不声称当时评审了所有限流算法。

## 决策与理由

`rate_limit_buckets` 以数据库时间计算固定窗口，通过原子 `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` 消费额度，避免分离的 get/set 在并发下丢失计数。桶标识使用 HMAC，过期记录分批清理。

反馈创建和投票在读取 Session 后、业务事务外消耗额度，因此后续业务失败不会退还一次尝试。当前额度为反馈 5 次/分钟、投票 30 次/分钟。Better Auth 接入共享 consume，保留其 HTTP 429 处理；随机认证路径规范化为有限类别，避免路径无限产生桶。

数据库不可用时限流失败不放行。Vercel 使用已约定的平台客户端 IP 头；非 Vercel 环境不直接信任任意转发头，使用共享回退桶。

## 影响与代价

- 不新增 Redis，并发实例共享原子额度。
- 每次受限操作增加数据库工作量，数据库故障会影响登录或写操作；固定窗口在窗口边界可能出现集中请求。
- 当前业务限流只接入反馈创建和投票，不能宣称项目设置、状态管理等所有 Action 都已限流。
- 这是应用防刷措施，不替代平台的流量攻击防护；自托管时需要重新配置可信代理策略。

## 实施与验证

新增 migration `0001`，共享存储和认证/业务接入已存在。单元用例覆盖 429、路径归类、业务失败消耗额度和存储失败拒绝放行；并发集成用例已编写。历史完成报告明确真实 Neon 迁移和集成测试尚未执行，本次也未执行；使用该版本前需要在目标环境应用新增 migration。

## 重新评估条件

限流读写对数据库产生明显压力、需要更精细的突发控制或部署脱离 Vercel 时，重新评估存储、窗口算法与代理信任策略。
