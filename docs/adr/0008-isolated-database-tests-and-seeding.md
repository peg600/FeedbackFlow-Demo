## 背景与约束

唯一约束、并发配额、投票和限流需要真实数据库测试，核心 E2E 也会创建账号和反馈。用户询问能否直接使用 Neon 开发库；讨论指出自动测试会制造大量数据并清理记录，可能污染日常开发与演示数据，随后用户同意独立测试方案。

## 考虑过的方案

- 复用 develop/preview 数据库：配置少，但会混入测试数据，清理和并发测试风险更高；不采用。
- 在现有 Neon 项目中使用专用 test branch：复用平台，隔离数据，采用；不等于已经批准或完成云资源创建。
- 只校验连接地址：实现审查后增加库内身份标记，降低误填或误复用连接的风险。

## 决策与理由

集成测试、测试迁移和 E2E 必须显式提供 test pooled/direct URL 及允许的 endpoint，校验二者属于同一数据库、迁移使用 direct 连接，并拒绝已知应用连接和开发/生产别名。没有测试配置时失败，不回退到应用数据库。

写入前还需验证 `public.__feedbackflow_test_guard` 中的摘要与操作员持有的测试 token 匹配。标记不属于普通应用 migration，需在确认的测试库单独初始化；该措施依赖正确配置，不能保证抵御同时复制了标记和凭据的错误操作。

测试数据使用独立运行标识并精确清理自身记录，不全库清空。Playwright 使用独立端口、自己的服务器和测试认证配置。演示 Seed 采用显式目标与确认、只补缺失数据并保留用户修改，避免把演示准备做成破坏性重置。

## 影响与代价

- 真实数据库行为有专门验证路径，开发与演示数据不会被正常测试清理逻辑混用。
- 测试分支、身份标记和独立环境配置增加准备成本；新环境不能直接无配置运行完整 E2E。
- Demo Seed 可以面向非测试环境，因此不受 test guard 保护，必须单独核对 direct 连接和显式确认；生产操作仍遵守既有审批规则。它不是通用测试清理脚本。

## 实施与验证

当前已有 endpoint 校验、身份标记验证、迁移包装器、集成/E2E 配置，以及幂等 Seed。相关单元测试和集成用例已编写。2026-09-18 最终交付明确：专用 Neon test 分支尚未创建，真实迁移、Seed 和完整数据库测试尚未执行；本次不能把这些写成已完成。

## 重新评估条件

引入 CI 自动测试分支、并行 E2E 或多测试数据库时，需要扩展分支生命周期、标记发放与精确清理机制，继续禁止静默回退到开发或生产连接。
