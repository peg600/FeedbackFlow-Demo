# 0016 — 客户端操作失败必须可见

- 替代：无；补充 [0006](0006-standardized-server-action-errors.md) 的展示约束

## 背景与约束

Billing 的 Checkout 错误原本放在顶部普通状态段落，用户滚动到 Upgrade 按钮时容易看不到；自动轮询和焦点对账忽略失败。用户要求当前接口失败必须有 Toast 或字段红字反馈。创建项目与提交反馈还存在等待期间编辑字段后隐藏通用错误的问题。

## 考虑过的方案

- 仅保留顶部文案：改动少，但无法保证长页面可见，不采用。
- 全局拦截 fetch、增加通知依赖：无法自然处理 Server Action、Better Auth 和 SDK 各自协议，且现有组件可完成，暂不采用。
- 调用方显式处理、共享轻量错误 Toast：保留字段语义与既有错误协议，采用。

## 决策与理由

所有客户端操作显式处理业务失败、校验失败及网络异常。字段错误继续关联输入框和红字，通用错误可用表单级红字或 Toast；后端任务和 Webhook 不需要浏览器 Toast。读取页面继续使用 Next.js 错误边界。

Billing 使用 `ErrorToast`，通过 Portal 固定在视口底部，复用已有样式 Token，以 `role="alert"` 通知辅助技术，支持关闭、不自动消失、不抢焦点。一次只显示一条错误；同一连续后台故障关闭后不反复弹出，成功检查或新手动操作后重置。轮询仍有次数上限，不因展示错误而重建结账或授予权益。

创建项目和提交反馈的通用/网络失败不依赖整表快照；字段错误仍按对应提交值过滤，避免展示过期校验。

## 影响与代价

- 无新依赖、数据库迁移或支付权限变化。
- 新调用方仍需显式接入；共享组件不等于全局自动捕获全部请求。
- Toast 保留到关闭可能遮挡少量内容，用户可关闭；连续后台错误去重避免打断。

## 实施与验证

已实现并增加 Checkout/Portal/Refresh、轮询/焦点、Paddle 事件和表单编辑期间失败的回归测试。Billing 共 19 项组件测试；本次全量 51 个文件、242 项测试以及 lint、typecheck、生产构建均通过。实际 Toast 组件与生产 CSS 在 Chromium 中验证了 14 组滚动视口（宽 390—1280px、高 300/844px），确认可见、可关闭且无横向溢出。此隔离组件检查不等同于真实 Billing 支付 E2E；未部署或验证真实支付。

## 重新评估条件

出现多来源并发通知、需要跨路由保留通知或统一通知队列时再评估 Provider 或成熟通知组件。
